# DDD問題集作成ガイドライン

DDD学習用の問題集（`問題集/A_*.md` 〜 `問題集/Z_横断的問題.md`）を新規作成・改訂する際の共通ルール。カテゴリを問わず、新規作成・改訂・レビューのいずれの作業でもこのガイドラインに従う。

## 背景

E4（モジュール）カテゴリのレビュー中、E4-06「モジュールと境界づけられたコンテキストの違いを性質・規模・目的の観点で説明せよ」という問題に次の欠陥が見つかった。

- 模範解答が3×2の表（3つの観点×2つの対象）になっており、実質的に3つの異なる論点を1問に詰め込んでいた
- 「それぞれ何が異なるか説明してください」という問い方は、どの粒度・範囲まで答えれば正解なのか問題文だけでは決まらない
- 隣接するE4-07（モジュールとコンテキストのどちらで分割すべきかの判断基準）と論点が重複していた

この問題は他プロジェクト（DP-300資格学習）の問題集で蓄積した知見と同種の欠陥であり、DDD問題集にも同じ原則を適用する必要がある。ただしDDD問題集は選択式ではなく**記述式（自由記述）中心**という前提が異なるため、原則をそのまま輸入せず、記述式に合わせて読み替える。

## 0. このプロジェクトの前提（他プロジェクトとの違い）

- 出題形式は**記述式**が基本。選択式・穴埋め・build listのような形式は使わない（既存の`問題集作成_作業指示書.md`のフォーマットに従う）
- 習熟レベルは「知識確認／理解確認／応用」の3段階（DP-300側の「01_用語確認／02_応用問題」の2区分とは異なる）
- 用語表記は**日本語（原著の訳語）を主表記**にする。DP-300側の「英語名を主表記」ルールは適用しない。理由：教材が『実践ドメイン駆動設計から学ぶDDD実装入門』という日本語書籍であり、章まとめ・用語集も日本語で統一されているため
- 模範解答の根拠は必ず対応する`第XX章まとめ.md`・`用語集/第XX章_用語集.md`に取る。原著の英語表現（`Teams`・`SaaSovation`等の固有名詞）はそのまま引用してよい

## 1. 問題文は1問1論点にする

答えの中に性質の異なる論点（定義・仕組み・理由・比較・複数観点の対比表など）が混在する場合、1問にまとめず分割する。分割した問題は元の問題IDに枝番を付ける（例：`E4-06` → `E4-06-1`、`E4-06-2`）。**後続の問題IDはずらさない。**

### 判断基準

1. **模範解答が表形式（複数観点×複数対象のマトリクス）になっている場合は、観点ごとに分割できないか検討する。** 表の列（観点）が2つ以上あり、かつ各列が独立して意味を成す場合は分割候補
2. **知識確認の列挙問題と理解確認の比較問題を1問に混在させない。** 「AとBの違いを、定義と使い分け基準の両方から説明せよ」のような問いは、「違いの定義」（知識確認）と「使い分け基準」（理解確認・応用）に分ける
3. **分割後の1問が、別の既存問題（同カテゴリまたは近接カテゴリ）とほぼ重複する場合は、分割ではなく統合・削除を検討する。** 例：E4-06の「目的」列とE4-07の分割基準は同じ論点なので、片方に寄せる
4. **問題数が増えることを理由に分割を避けない。** ただし増設は「問題集の分類.md」の重要度が高いカテゴリ（集約・ドメインサービス・BC統合など）を優先する

## 2. 抽象的な「〜について説明してください」を避ける

**判定基準は表現パターンの一致ではなく、「答えの形式・範囲が問題文だけで確定しているか」という構造で判断する。** 次の表現はすべて同じ構造上の欠陥を持つ可能性がある。文言が違うという理由で見逃さない。

- 「〜とは何ですか」「〜について説明してください」
- 「〜はそれぞれ何が異なるか説明してください」（観点が問題文中に列挙されているだけで、各観点の答え方が確定していない）
- 「どのような関係になりますか」「どう違いますか」（比較の軸が示されていない場合）
- 複数の固有名詞・観点を問題文中に列挙しているが、それぞれ独立した問いに分けていないもの

判定は「この問題は、模範解答を書く前に、回答者が答えの粒度・範囲・観点の数を自分で決めなければならないか」を自問して行う。YESなら曖昧と判定し、次のいずれかで具体化する。

### a. 観点を1つに絞った問いにする

```
改訂前: 「モジュール」と「境界づけられたコンテキスト」は、性質・規模・目的の観点でそれぞれ何が異なるか説明してください。

改訂後（分割）:
- モジュールと境界づけられたコンテキストは、それぞれ何を実現するための仕組みか（性質の違い）を説明してください。
- モデルが成長する過程で、モジュールと境界づけられたコンテキストのどちらで分割すべきかを判断する基準は何ですか。（→目的の観点はE4-07に統合）
```

### b. 具体的なシナリオ設定にする

抽象的な比較を問うより、具体的な状況を提示して「この状況はどちらに該当するか、なぜか」を問う方が、丸暗記でなく理解を確認できる。

```
改訂前: PLEは何ですか。

改訂後: チームが「同じ用語が2つの意味で使われていて会話がかみ合わない」と気づいた。これはモジュール分割で解決すべき問題か、境界づけられたコンテキスト分割で解決すべき問題か、理由とともに述べよ。
```

### c. 「なぜ」を問い、仕組みの理解を確認する

「〜とは何ですか」ではなく「なぜそうなっているか」を問うことで、定義の暗唱ではなく理解を確認する。既存の`問題集作成_作業指示書.md`の「理解確認」レベルはこの形式を標準としている。

### d. 具体化したつもりでもまだ答えづらいパターンを見抜く

- 観点を絞ったつもりでも、その観点自体の答えが2つ以上の下位論点を含んでいる（例：「性質の違い」の答えに「プログラミング的な仕組みか、ビジネス的な境界か」という対比と「どちらが技術寄り・ビジネス寄りか」という理由の両方が必要な場合、さらに分割が要るか検討する）
- 応用問題のシナリオが抽象的すぎて、DDDの原則を知らなくても常識だけで答えられてしまう（例：「効率を上げるにはどうすればよいか」のような一般論で答えられる問いは、DDD固有の判断軸を問えていない）
- 比較を求める問題なのに、比較対象の片方の情報しか問題文に与えられていない

## 3. 教材の原文を確認してから答えを作る・訂正する

ユーザーから「本当にそうなのか」「原著にそう書いてあるのか」と問われた場合、記憶や一般論で答えず、該当章の`第XX章まとめ.md`・`用語集/第XX章_用語集.md`を確認してから回答する。

新規問題を作成する際も、模範解答は必ずこれらのファイルの記述から作成する。独自解釈で書かない（`問題集作成_作業指示書.md`ですでに定めている原則を踏襲する）。

## 4. 用語集との突き合わせで出題漏れを洗い出す

各章には`用語集/第XX章_用語集.md`が存在する。カテゴリの問題群を作り終えた節目、またはユーザーから「見落としがないかレビューして」と頼まれた段階で、用語集を基準に出題漏れを洗い出す。

**レビュー手順**:
1. 対象カテゴリに対応する章の用語集にある見出し語を一通り確認する
2. 各見出し語について、カテゴリの問題集ファイル内を検索し、**問題文または模範解答の主題として**登場しているかを確認する
3. 他の問題の模範解答中に**説明の一部としてのみ**登場し、独立した問題の主役になっていない語は、出題漏れの候補として洗い出す
4. 候補のうち、「問題集の分類.md」の重要度が高い論点・設計判断に直結するものを優先して新規問題を追加する

## 5. 隣接問題との重複・参照禁止のセルフチェック

`問題集作成_作業指示書.md`のレビュー観点にある「他の問題を参照してはいけない」ルールを、新規作成時にも事前チェックとして適用する。

- 新規問題の問題文が、同カテゴリ内の他の問題を読まないと答えられない前提を含んでいないか
- 新規問題の論点が、同カテゴリまたは近接カテゴリ（例：E4とB、D2とD3）の既存問題と実質的に同じ問いになっていないか

重複が見つかった場合、新設せず既存問題への統合を優先する（1節の判断基準3と同じ）。

## 6. 番号管理と出題運用

- 出題する直前に「今から出すのは問題{ID}」と番号を明示し、都度ファイルを参照して確認する（記憶だけで進めない）
- 進捗ファイル（`問題集/進捗/第N周_進捗.md`）の該当周の表と照合し、まだ結果が埋まっていない最小番号の問題を次に出す
- 1問の採点・記録が終わったら、**ユーザーの明確な指示を待ってから**次の問題を出す
- 問題を分割・改訂したら、カテゴリファイル（問題文）と全ての周の進捗ファイル（進捗表・分母の問題数）を同期して更新する（`問題集作成_作業指示書.md`のレビュー後の修正ルールを参照）

## 7. 問題集を作ること自体を目的化しない

問題集・進捗表は、自分が実装するとき、DDDに基づいた設計を実行できる状態になるための手段であり、周回数・問題数の消化そのものが目的ではない。この本にだけ出てくる事例や図表・ルールの番号の暗記も目的ではない。

- 降参・不正解の項目は、答えを教えて終わりにせず、ユーザーが疑問を持った箇所を深掘りし、自分の言葉で説明できる状態を目指す
- 同じ問題を再度出題して定着を確認する、関連する章まとめ・用語集に接続するといった対応を優先する
