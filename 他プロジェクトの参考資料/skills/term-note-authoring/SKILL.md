# 用語ノート作成

問題集作成キット v1.1（2026-10-08）。原本はDP-300ボールトの `問題集作成キット/`。

着手前に **[project.md](project.md)** を読む。用語集・用語ノートの置き場所、原文の場所、使える表現形式はそこで決まる。

## 1. 用語集と用語ノートの使い分け

同じ「用語を整理する」ノートでも、用語集と用語ノートは役割が異なる。

- **用語集**（単元ごとに1つ）: その単元で登場した用語を辞典形式（`### 用語名` → 説明の段落）で網羅的に一覧化する。問題集（一問一答）と役割が重なるため、一問一答形式にはしない
- **用語ノート**（概念ごとに個別ファイル）: 複数単元・複数問題集にまたがって登場する重要概念を深掘りする。用語集の該当項目からリンクする

新しい単元の用語集を作る際は、その単元の原文・問題集に登場した用語を一通り確認し、辞典形式で列挙する。特定の概念が繰り返し登場し、掘り下げる価値がある場合だけ、用語ノートに切り出す。

## 2. 切り出しのきっかけを見逃さない

問題集で不正解・理解不足が発覚した論点のうち、次のいずれかに該当するものは用語ノート化を提案する。

- 複数の選択肢・モデル・機能が対比構造になっている（例（DP-300）: 購入モデル、サービスレベル、デプロイモデル）
- 複数単元・複数問題集にまたがって同じ概念が繰り返し登場する
- 一問一答では、答えの奥にある「なぜその選択肢が存在するか」という設計思想が伝わらない
- 文章での説明を繰り返しても伝わらない（図解など表現形式を変えるべきサイン）

## 3. 作成手順

1. **原文を確認する**: 記憶や一般論で書き始めない。該当単元の原文ファイルを検索し、既存の問題集・用語集の記述との差分（見落とし・不足）がないか確認する
2. **情報の構造を見極めてから、伝わる表現を選ぶ**: 表現方法を先に決めない。対象の情報の構造を先に判断し、その構造が最も伝わる形式を後から当てはめる。1つのノートに複数の形式を併用してよい
   - 選択肢が並列（二択・三択など）で、性質を横断比較したい → **比較表**
   - 「Aを選んだら次にBを選ぶ」という逐次的な依存関係がある → 見出しの親子関係で示す（手順3）。分岐が3段階以上なら **mermaid flowchart** で決定木を補う（実線=主要フロー、破線=制約・副次的な関連）
   - 「コスト vs 性能」のような2軸上の相対的な位置を伝えたい → **mermaid quadrantChart** などの散布図。軸の異なる要素を混在させない
   - 選択肢ごとに用途・強み・弱み・向かない場面を塊として覚えたい → **カード形式の箇条書き**
   - 色分けやセル結合など、標準markdownで表現しにくい強調が理解に不可欠 → **HTML埋め込み**を検討してよい。ただし、Obsidianの内部リンク`[[ ]]`はHTMLタグ内で機能しないため多用しない

   判断基準は常に「暗記ではなく、対比・判断を助けるか」。表現方法を選ぶこと自体を目的化しない。使える形式（mermaidが表示されるか等）はproject.mdの前提に従う
3. **見出しレベルで親子関係（包含関係）を明示する**: 「Aを選んだ後にBを選ぶ」という依存関係があるなら、Bの見出しをAの子見出しにする（`##`→`###`）。同列に並べると、独立した選択肢に見えて誤解を招く
4. **実務シナリオで具体化する**: 抽象的な分岐軸は、対極的な2つの業務シナリオに当てはめる（例（DP-300）: 高トランザクション処理 vs 大量データのマルチテナント構成）。そのうえで、どういう観点（負荷パターン、データ構造、伸び方など）からその判断に至ったかを明示する。結論だけでなく、判断の観点を書く
5. **既存ノートと相互リンクする**: 用語集の該当項目、関連する問題集の問題番号と双方向にリンクする

## 4. レビュー観点

- 見出し階層は、実際の依存関係（親子・並列）と一致しているか
- 表・図は「暗記」ではなく「対比・判断」を助ける形になっているか
- 原文にある要素を見落としていないか（特に「もう1つの分岐」を書き忘れていないか）
- 抽象的な選択肢のまま終わらず、シナリオで具体化されているか
- 原文のコード例を引用する場合、同じ識別子が別のものを指していないか（quiz-authoring skill 2-gと同じ基準）
