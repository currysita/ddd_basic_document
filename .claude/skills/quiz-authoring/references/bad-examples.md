# 問題集の悪い実例集

問題集で実際に作成し、ユーザーから指摘を受けて改訂した「絶対に繰り返してはいけない」問題文・回答の実例を記録する。[guideline.md](guideline.md)が「良い作り方」の例を示すのに対し、こちらは「実際にやらかした失敗」だけを集めた事例集。実例はDP-300（Azure SQL）の問題集で起きたものだが、パターンは分野を問わない。

新規作成・改訂で問題文を書いたら、出題前にここに載っている実例と同じパターンになっていないか確認する（SKILL.md 2-i 提示前ゲートの一部）。

---

## 実例1: 否定形の連続・二重否定

**発生箇所**: DP-300 試験対策問題集 問題10-1-1（Log Replay Serviceの利用理由）

### 悪い例（実際に出題してしまった問題文）

**問題**: 次のうち、Log Replay Service の利用を検討すべき理由として**当てはまらない**ものはどれですか。

A. DMS（Azure Data Migration Service）実行可能ファイルを環境にインストール**できない**
B. データベースバックアップへのファイルアクセスが**ない**
C. 環境から Azure へのネットワークポートを一切**開けない**
D. 移行プロジェクトをより詳細に制御したい

### 何が悪いか

- 問題文が「当てはまらないものは」という**二重否定**（除外条件を問う否定形の設問）
- 選択肢A・B・Cがそれぞれ「〜できない」「〜がない」「〜開けない」という**否定形の連続**
- 読み手は「二重否定を反転して読む」→「さらに各選択肢内の部分否定を読む」という二重の変換処理を強いられる
- 唯一の肯定形選択肢（D）が視覚的にも構造的にも浮いて見え、消去法で不自然に選びやすくなる（正解の伏線が漏れる）

ユーザーからの指摘: 「この問題は『ない』ばかりで非常に解りづらい。直してくれ」

### 改訂後（肯定形に統一）

**問題**: Log Replay Service の利用を検討する理由として、原文に明記されているものはどれですか。

A. DMS（Azure Data Migration Service）を使ったオンライン移行より高速に完了させたい
B. 移行プロジェクトをより詳細に制御したい
C. Azureへのネットワーク接続を一切確立せずに移行を完結させたい
D. バックアップを一切取得せずに移行を完結させたい

**答え**: B。

### 何を変えたか

- 問題文を「当てはまらないものは」→「明記されているものは」という肯定の問いに変更
- 除外したい要素（ネットワーク不要・バックアップ不要）は、否定形の言い回しではなく「矛盾する具体的な事実」として選択肢に埋め込んだ（C・Dは、LRSの実際の仕組みと論理的に矛盾する内容にすることで誤答として機能させている）

### 再発防止の原則

1. 選択肢を書き終えたら、**全選択肢の語尾を眺めて否定形が2つ以上連続していないか**を確認する
2. 問題文が「当てはまらないものは」「誤っているものは」のような除外形になっている場合、選択肢は原則として肯定形で統一する
3. 除外させたい要素を作りたい場合は、否定語（〜ない、〜できない）に頼らず、**事実として矛盾する内容**を選択肢の文として書く

## 実例2: 常識・直感だけで正解できる選択肢

**発生箇所**: DP-300 試験対策問題集 問題10-1-1（旧版、実例1とは別の改訂前）

### 悪い例

**問題**: Log Replay Service は、オンプレミスから SQL Managed Instance への移行において、オンライン・オフラインのどちらの移行オプションですか。

A. オンライン
B. オフライン

### 何が悪いか

「移行」という文脈で「オンライン・オフラインのどちらか」を問うと、一般常識・直感だけで「オンライン」を選びやすく、LRSという固有の知識を測れていない。もっともらしい誤答を用意できない設問は、理解度を測る問題として機能しない。

### 再発防止の原則

選択肢案を書いた時点で「知識ゼロの人でも直感・常識だけで正解できないか」を自問する。できてしまう場合は、別の切り口（利用理由の具体的な列挙、他の類似サービスとの比較など）に作り直す。

## 実例3: 原文の同一文からの機械的な分割で、片方が独立論点を持たない

**発生箇所**: DP-300 試験対策問題集 問題10-2-2（ネイティブ バックアップと復元を好む立場）

### 悪い例（実際に出題してしまった問題文）

**問題**: ネイティブ バックアップと復元による移行は、多くのどのような立場の人が好むシンプルな移行方法ですか。

**答え**: 多くのSQL Serverプロフェッショナル。

### 何が悪いか

原文は「バックアップと復元は、多くのSQL Serverプロフェッショナルが好むシンプルな移行方法である。これは、Azure Storageにデータベースの完全バックアップを提供できる顧客にとって最も簡単な移行オプションである」という**1つの文**。これを「誰が好むか（10-2-2）」と「どんな条件の顧客に最適か（10-2-1）」の2問に分割したが、前者は「多くのSQL Serverプロフェッショナル」という一般論にすぎず、DBAでもデータエンジニアでも当てはまりそうで、設計判断・シナリオ判断につながる知識になっていない。

ユーザーからの指摘: 「この問題は解答が漠然としています。作り直してください。」

### 改訂後（統合）

「誰が好むか」の問いは削除し、10-2-1（条件面を問う選択式）に一本化した。原文の同じ一文から複数の論点を無理に切り出すのではなく、実質的に測れる知識（Azure Storageに完全バックアップを提供できる顧客に最適、ダウンタイムはゼロにならない）だけを残した。

### 再発防止の原則

1. 原文の1つの文から複数問を作る前に、それぞれの問いが独立した論点（比較・判断基準・具体的な条件）を持つかを確認する。「主語は誰か」「目的語は何か」のような機械的な要素分割は、論点の分割にならないことが多い
2. 答えが「多くの〜」「一般的に〜」のような曖昧な集合を指すだけで、具体的な判断基準（条件・比較・理由）を伴わない場合は、その問い自体を疑う

## 実例4: 「併用」選択肢が他の選択肢の単語をそのまま含み、入れ子に見える

**発生箇所**: DP-300 試験対策問題集 問題10-1-10（LRSの中間ストレージに対する認証方法）

### 悪い例（実際に出題してしまった問題文）

**問題**: 中間ストレージに対する認証方法として使えるのはどれですか（複数選択）。

A. SAS トークン
B. マネージド ID
C. SAS トークンとマネージド ID の併用

**答え**: A, B（SASトークンかマネージドIDのどちらか一方）。

### 何が悪いか

- 選択肢Cの文中に、選択肢A・Bの単語がそのまま埋め込まれており、A・B・Cが並列の独立した選択肢に見えず、C自体が「AとBを合成した入れ子」に見える
- 「複数選択」という指示文と、「A、B、その両方＝C」という択一的に見える選択肢構造が矛盾して見え、そもそも「A・Bを両方選ぶ」のか「Cを選ぶ」のかが紙面上わかりにくい
- 実際に出題した結果、回答者は「AとBはありえるかもしれないが、CはAとBに見えてしまう」と混乱した。正解が実際にはA・Bの2つであり、Cはその単純な誤答であるにもかかわらず、Cの存在自体が正解の理解を妨げてしまった

ユーザーからの指摘: 「問題の出し方が解りづらいよ。AとBはありえるかもしれないけど、CはAとBに見えちゃう。」

### 改訂後（無関係な選択肢に置き換え）

**問題**: 中間ストレージに対する認証方法として使えるのはどれですか（複数選択、2つ選ぶ）。

A. SAS トークン
B. マネージド ID
C. Windows 統合認証
D. SQL Server 認証

**答え**: A, B。CのWindows統合認証、DのSQL Server認証は、いずれもSQL Serverインスタンスへの接続認証であり、Blob Storageへのアクセス認証とは無関係。

### 再発防止の原則

1. 複数選択問題で「A・Bのどちらも正解」にしたい場合、A・Bを合成した「Cとして両方を併記する」選択肢を作らない。代わりに、AやBとは無関係な文脈から誤答の選択肢（C、D...）を用意する
2. 「〜の併用」「AとBの組み合わせ」という文言を選択肢に書きたくなったら、それは「正解が複数ある問題を、択一問題の形式に押し込もうとしている」サインである。素直に「複数選択、2つ選ぶ」と明示し、選択肢は独立した候補として並べる
3. 選択肢を書き終えたら、「ある選択肢の文中に、別の選択肢の単語がそのまま入っていないか」を確認する

## 実例5: 「〜とは何ですか」型の抽象的な自由記述

**発生箇所**: DP-300 試験対策問題集 ラーニングパス2_問題集.md 問題2-3（Microsoft Entra認証と他Azureリソースの資格情報共有）

### 悪い例（実際に出題してしまった問題文）

**問題**: Microsoft Entra認証をAzure SQL Databaseで使う場合、ユーザーはAzure PortalやMicrosoft 365など他のAzureリソースへのサインインと、どのような関係になりますか。

**答え**: 同じ資格情報（アカウント）を使い回せる。

### 何が悪いか

- 「どのような関係になりますか」という問いは、答えの範囲（形式・粒度）が全く指定されておらず、実質的に「〜とは何ですか」と同じ曖昧さを持つ
- 選択式・二択・シナリオ・穴埋めのいずれの具体化技法も使われておらず、SKILL.md 2-c（抽象的な問いを避ける）に反する
- 提示前ゲート（新規作成・改訂した問題は4節のチェックリストを実行するまでユーザーに見せない）を通さずに出題してしまった

ユーザーからの指摘: 「問題が曖昧すぎる。」

### 再発防止の原則

1. 「どのような関係になりますか」「どう影響しますか」「どのように扱われますか」のような、結論の形式が定まらない問いは、「〜とは何ですか」と同種の抽象問題として扱い、具体化技法（選択式・シナリオ・二択・「なぜ」・穴埋め）のいずれかに変換してから出題する
2. 原文の1文が単一の事実（例: 「同じ資格情報を使う」）を述べているだけの場合、その事実ともっともらしい誤答（例: 「別々に管理する必要がある」「Entra認証を使うと他リソースへのアクセスも自動的に許可される」）を選択肢化するだけで具体化できることが多い。自由記述のまま残す理由にはならない
3. 新規作成・改訂した問題文は、出題前に必ずSKILL.md 2-i 提示前ゲート（4節チェックリスト）と、この実例集を照合してから見せる

## 実例6: 「〜とは何ですか」型の判定を、表現パターンの一致だけで行い、同種の別表現を見逃した

**発生箇所**: DP-300 試験対策問題集 ラーニングパス2_問題集.md 全体のレビュー（問題9-4、11-2、18-1、21、22-1）

### 悪い例（実際に起きた経緯）

実例5（問題2-3）の指摘を受け、ラーニングパス2の問題集全体を「抽象的な問い」の観点でレビューするサブエージェントを立てた。このレビューは「〜とは何ですか」「どのような関係になりますか」など複数パターンを対象に含めるよう明示的に指示していたにもかかわらず、次の5問を「二択+理由」「なぜ」の技法を使っているという理由だけで**修正不要（据え置き）と判定してしまった**。

- 問題9-4: 「TDEで使用した証明書を手動でバックアップし、安全に保存しておく必要があるのはなぜですか。」（選択肢なし）
- 問題11-2: 「決定論的暗号化とランダム化された暗号化のどちらを使うべきですか。またその理由は何ですか。」（選択肢なし）
- 問題18-1: 「〜攻撃手法を何と呼びますか。」（専門用語1語の想起、選択肢なし）
- 問題21: 「TDE・Always Encrypted・動的データマスク・RLSのうち...どれですか。」（4項目を地の文で列挙しているだけで、A/B/C/Dの選択肢として明示されていない）
- 問題22-1: 「更新可能な台帳テーブルとAppend-only台帳テーブルのうち...どちらですか。またその理由は何ですか。」（選択肢なし）

ユーザーからの指摘: 「今回の問題のような『どのような関係になりますか』『どのような●●なりますか』形式を、これ以降も調査して改善してくれ...これでは信頼できない。」

### 何が悪いか

- 「技法（シナリオ・二択・『なぜ』）を使っている」ことと「答えの形式が選択肢で確定している」ことを混同した。技法2〜4は選択肢を作るための土台であり、選択肢そのものの代わりにはならない
- レビュー観点が「表現パターンが一致するか」（「〜とは何ですか」という文字列があるか）という表層的な照合になっており、「回答者が答えの形式・範囲を自分で決めなければならないか」という構造的な判定になっていなかった
- 一度目のレビュー（原文突き合わせ＋抽象問題の改善）でも、二度目のレビュー（曖昧表現パターンの調査）でも、同じ種類の欠陥が生き残った。「探す観点をリストアップして探す」だけでは、リストにない・リストの精神を汲み取れない表現を取りこぼす

### 改訂後

5問すべてを選択式（A/B/Cの3択、または4択）に変換した。もっともらしい誤答は、原文にある関連する仕組み（TDEの証明書の役割、暗号化方式の特性、SQLインジェクションとの違いなど）から作成した。

### 再発防止の原則

1. 「〜とは何ですか」型の判定は、個別の言い回しのリストに頼らず、**「選択肢を見なくても回答者が答えの粒度・範囲を自分で決めなければならないか」を1問ずつ自問する**という構造的な基準で行う（SKILL.md 2-cを参照）
2. シナリオ・二択・「なぜ」の技法を使っている問題を見て「技法を使っているから曖昧ではない」と早合点しない。**技法を使った上で選択肢（A/B/Cなど）が明示されているか**を必ず別途確認する
3. レビューを依頼する際は、判定基準そのもの（表現パターンの網羅ではなく構造的な自問）をレビュー担当に明示的に伝える。パターンの列挙だけを渡すと、リストにある表現の再現だけを探して終わる

## 実例7: 同名の識別子を複数使うSQL構文を、区別なくそのまま引用した

**発生箇所**: DP-300 試験対策問題集 ラーニングパス2_問題集.md 問題4-1-1a（demoユーザーへの直接GRANT手順）

### 悪い例（実際に出題してしまった問題文）

**選択肢**: 対象データベースに接続し、`CREATE USER demo FROM LOGIN demo`を実行する

### 何が悪いか

- 原文のコード例（`CREATE USER demo FROM LOGIN demo`）をそのまま引用したが、「demo」という同じ文字列が2回登場しており、どちらが「これから新規作成するユーザー名」でどちらが「既に存在する既存のログイン名」なのか、SQL構文を熟知していない回答者には区別がつかない
- 原文がこの命名慣習（新規オブジェクトと紐づけ先オブジェクトに同じ名前を使う）を採用しているのは、実務上の分かりやすさのためだが、問題文にそのまま持ち込むと初学者にとってはかえって混乱を招く
- ログインとユーザーが別のオブジェクトであり保存場所も異なる、という直前に説明した概念の理解を、この構文がかえって曖昧にしてしまった

ユーザーからの指摘: 「これ問題文がおかしくないですか？demoとdemoが何のdemoなのか解らない」

### 改訂後・第1版（括弧書きで注記）※この対応は不十分だった

**選択肢**: 対象データベースに接続し、`CREATE USER demo FROM LOGIN demo`（新しく作るユーザー名`demo` FROM 既存のログイン名`demo`）を実行する

解説にも「同じ『demo』という文字列が2回出てくるが、指しているオブジェクトは別」という一文を追加し、加えて深掘り用語ノート`ログインとユーザーの違い`を新設して、構文の読み方と保存場所の違いをmermaid図付きで集約した。

**しかしこの対応は不十分だった**。再出題した際、ユーザーから「これ、本当に分かりやすいと思います？私がdemoという単語を用いたら貴方は解りますか？」と再度指摘され、Claude自身も「demo」という単語だけでは2つのうちどちらを指すか判別できないことを認めた。「じゃあ駄目じゃねえか。私が質問を返せないだろ」という指摘の通り、括弧注記は「同じ単語が2回出てくる」という構造そのものを変えておらず、単語を見た瞬間の判別可能性は改善していなかった。

### 改訂後・第2版（名前自体を変える）

**選択肢**: 対象データベースに接続し、`CREATE USER SalesUser FROM LOGIN demo`（ログイン`demo`に紐づく、新しいユーザー`SalesUser`を作る）を実行する

ログイン名は原文通り`demo`のまま維持し、**これから新規作成するユーザー名だけを`SalesUser`という別の単語に変更**した。これにより、括弧注記に頼らず、見た目だけで「ログインとユーザーは別物」と分かるようになった。用語ノート`ログインとユーザーの違い`も同様にユーザー名を`SalesUser`に統一し、「原文は両方とも同じ名前を使っているが、この問題では区別のために別の名前にしている」という説明を追加した。

### 再発防止の原則

1. 原文のSQLコード例をそのまま問題文・選択肢に引用する際、同じ識別子（変数名・ユーザー名など）が2回以上登場していないか確認する
2. **登場している場合、第一の対応は名前自体を変えること。** 片方の識別子だけを別の単語に置き換えれば、注記なしで見た目から区別できる。括弧書きでの注記は、名前を変えられない場合の次善の策に留める（名前を変えた上で、原文との対応関係を説明する注記を添えるのはよい）
3. 同じ構文が複数の問題にまたがって登場する場合、問題ごとに繰り返し説明するのではなく、深掘り用語ノートに集約して各問題からリンクする
4. 原文のコード例をコピーするだけで満足せず、「対象分野の知識がない人に、この構文を声に出して読んでもらったら、各識別子が指すものを区別できるか」を自問する（SKILL.md 2-g参照）。一度「注記を足せば直った」と判断しても、実際にユーザーに読ませて確認するまでは解決したと決めつけない

## 実例を追加する際の書式

新しい実例は、上記の実例と同じ構成（発生箇所／悪い例／何が悪いか／改訂後／再発防止の原則）で追記する。ユーザーからの実際の指摘があれば、その言葉もそのまま引用して残す（何を不快に感じたかが再発防止の手がかりになるため）。
