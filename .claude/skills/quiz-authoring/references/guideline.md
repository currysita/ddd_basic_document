# 問題集作成ガイドライン（悪い例・改善例）

SKILL.mdの各ルールを、具体例で補足する。節番号はSKILL.mdに対応する。例はDP-300（Azure SQL）の問題集から採ったものだが、示している原則は分野を問わない。

## 背景

最初の問題集を周回する過程で、次のような欠陥が繰り返し見つかった。

- 「〜とは何ですか？」という問い方だけでは、答えに複数の論点（定義・仕組み・理由・比較）が混在し、丸暗記になりやすく採点も曖昧になる
- 抽象的すぎて、何を答えれば正解なのか的が絞りにくい
- 実務での使われ方（どこで実行するか、どう呼び出されるか）を反映していない問題文だと、試験にも実務にも役立たない理解のまま覚えてしまう

## 2-b. 1問1論点に分割する

**改訂前**（1問に3つの論点が混在）:
```
Dynamic Threshold（動的しきい値）とは、Azure Monitor のアラートにおいてどのような機能ですか？

答え: メトリックの履歴動作を機械学習で学習し、リソースの動作が異常になったときに自動でアラートを生成する機能。
ワークロードの季節性（曜日・時間帯による変動）を検出してしきい値を自動調整するため、静的しきい値より柔軟なアラート設定が可能。
```

**改訂後**（3問に分割）:
```
問題3-1: Seasonality（季節性）とは、時系列データの分析においてどのような概念ですか？
問題3-2: Dynamic Threshold は、何をもとに、何を検出しますか？
問題3-3: Dynamic Threshold は、静的しきい値と比べてどのような場面で有効ですか？
```

- 3-1で前提となる一般用語を独立して問う
- 3-2で仕組みそのものを問う
- 3-3で実務判断（いつ使うべきか）を問う

注意: この分割例は論点の切り分けを示すもの。分割後の各問も、2-cに従って選択肢を明示する必要がある。

**模範解答が表形式（条件2）の例【記述式】**（DDD書籍の問題集から）:
```
改訂前: 「モジュール」と「境界づけられたコンテキスト」は、性質・規模・目的の観点でそれぞれ何が異なるか説明してください。
（模範解答が3観点×2対象の表になっており、3つの論点を1問に詰め込んでいた。隣接問題「どちらで分割すべきかの判断基準」とも「目的」の観点が重複していた）

改訂後:
- モジュールと境界づけられたコンテキストは、それぞれ何を実現するための仕組みか（性質の違い）を説明してください。
- 「目的」の観点は、隣接する判断基準の問題に統合した（条件3）
```

**負荷の混在（条件1）の例**: 「4機能をA/Bに分類し、かつ代替手段の名称も書かせる」問題は、分類問題（選ぶ）と想起問題（書く）に分ける。

**「AまたはB」（条件4）の例**: 「`GRANT`または`ALTER ROLE`でアクセス許可を与える」という選択肢は、性質の異なる2つの状況を「または」に圧縮していた。

- 単一ユーザーへの直接付与: GRANTだけで完結する
- 複数ユーザーが同じ権限を持つロール経由の管理: GRANT（ロールへの権限付与）とALTER ROLE（メンバー追加）の両方が、別の役割で必要になる

状況ごとに2問に分割した。

**機械的な要素分割（条件5）の例**: [bad-examples.md 実例3](bad-examples.md#実例3-原文の同一文からの機械的な分割で片方が独立論点を持たない)。

## 2-c. 抽象的な問いを具体化する

### 技法1: 選択式にする

```
改訂前: Perfmon（Performance Monitor）とは何ですか？
改訂後: SQL Server をインストールした Azure 仮想マシンに対して Perfmon を使いたいとき、どこで実行しますか？
  A. Azure Portal
  B. Azure CLI
  C. 対象のWindows（SQL Serverをインストールした仮想マシン）にログインして実行する
```

模範解答に複数の論点（例: 「何で書くか」「どこで動くか」）が含まれる場合は、1つの文に複数の空欄を作り、**空欄ごとに独立した選択肢群**を用意する形式も使える。

```
CLR統合では、（　A　）で書いたコードをストアドプロシージャ・関数として登録し、（　B　）として実行される。

空欄Aの選択肢: 1. C#/.NET  2. Python  3. PowerShell
空欄Bの選択肢: 1. OS上に常駐する別サービス（外部プロセス）  2. SQL Serverプロセスの内部の一部  3. Azure Functions上のサーバーレス関数
```

穴埋めにすると教材の言い回しを暗唱するしかない語（例: 「SQL Serverプロセス」）も、選択肢に対比先（外部プロセス）を含めれば、丸暗記ではなく対比の理解を問える。

### 技法2: 具体的なシナリオ設定にする

```
改訂前: Action Group（アクション グループ）とは何ですか？
改訂後: 複数のアラート ルール（CPU高負荷・ディスク容量・メモリ不足など）があり、いずれも同じ担当者にメール通知とSMS通知の両方を送りたいとします。この場合、Action Group はいくつ作成する必要がありますか？
  A. 1つ  B. 2つ（メール用・SMS用）  C. アラート ルールの数だけ  D. アラート ルールの数×2
```

### 技法3: 比較にする

```
改訂前: PLEは何ですか？
改訂後: VM上のSQL Server固有のメトリック（例: PLE）を取得できるのはどれですか？
  A. Azure Monitor の標準メトリックだけ
  B. Perfmon だけ
  C. どちらでも同じように取得できる
```

本試験で二択が出ない場合（project.md参照）は、比較の軸を保ったまま3択以上にする。

### 技法4: 「なぜ」「どの段階か」を問う

```
改訂前: Action Groupとは何ですか？
改訂後: Azure Monitor の監視の流れは「収集・検知・対応」の3段階に分かれます。Action Group はこのうちどれに該当しますか？
```

### まだ答えづらいパターンの例

**観点の数を選択肢が反映していない**:
```
改訂前: T-SQLで正規表現・独自アルゴリズムのような手続き型ロジックを書くと、一般的にどうなりますか？
（模範解答が「書きにくい」「低速」の2観点を含むのに、自由記述のまま）

改訂後: 次からすべて選んでください。
（複数選択）
  A. コードが書きにくくなる
  B. 実行が低速になりがちである
  C. コードが書きやすくなる
  D. 実行が高速になる
  E. コンパイルエラーになり実行できない
```

**複数項目の列挙を自由記述にしている**: 「4機能のうち代替手段がないのはどれとどれですか」は、答えの数を示していても項目名を書く負担が残る。「A. 複数DBクエリ・CLR　B. CLR・システムDBアクセス ...」のように組み合わせを選択肢にする。

**空欄が1つの穴埋め**: 「Xとは何ですか」と同じ曖昧さが残る。空欄が複数あると、前後の文脈が互いの手がかりになって範囲が絞られる。

**常識・直感で正解できる**: 「移行」という文脈で「オンライン・オフラインのどちらか」を問うと、知識がなくてもオンラインを選べる（[bad-examples.md 実例2](bad-examples.md#実例2-常識直感だけで正解できる選択肢)）。

**「新しい／大きい方が正解」という単調な軸**: 「安全なTLSバージョンはどれか。A. TLS 1.0 B. TLS 1.1 C. TLS 1.2」は、「新しいほど安全」という常識だけで解ける。原文で言及されているさらに新しい版（TLS 1.3）を混ぜ、「原文が推奨と明記している版はどれか」を問うと、単調な必勝法が機能しなくなる。

**否定形の連続・二重否定**: [bad-examples.md 実例1](bad-examples.md#実例1-否定形の連続二重否定)。

### 穴埋めの文法検証の実例

「①_______な処理」という空欄に「単なるデータのインポートのよう」を代入すると、「単なるデータのインポートのような処理」という意味不明な文になった。選択肢を直すのではなく、骨格側（対比構造を地の文に固定する）を直す。

さらに、「RESTOREはネットワーク帯域を大量消費する処理」のような、文脈上ありえない誤答しか作れない空欄があった。これは文法の問題ではなく、その空欄が独立した1問にすべき論点だった。分割して2問にしたところ、それぞれに実在する紛らわしい選択肢を使えるようになった。

## 2-h. 基礎的な前提が抜けた例

- **正式名称が抜けた**: Log Replay Service（LRS）について、「利用理由」「事前作成の要否」「30日の期限」を先に問題化したが、「LRSは何の略か」を問う問題がなかった。ユーザーから「LRSってそもそも何でしたっけ」と聞かれて発覚した
- **目的が抜けた**: 「Managed Instance リンクは、何という技術を使いますか」（技術名）を作ったが、その手前に「Managed Instance リンクとは何をする機能か」を問う問題がなかった。ユーザーから「問題の意味がわからない。前提が抜けている」と指摘された

## 5. 用語集との突き合わせの実例

「SQL Agent機能はどちらで使えるか」という問題の答えに、「代替機能はエラスティック ジョブ」と書いていた。記述は正しいが、エラスティック ジョブという語は答え内のリンク表示としてしか登場せず、独立した問題の主役になったことがなかった。ユーザーから「関連する単語なのに答えに出てこない単語があるのでは」と指摘されて発覚した。新設時は、名前が似た「エラスティック クエリ」を誤答に混ぜて対比させた。
