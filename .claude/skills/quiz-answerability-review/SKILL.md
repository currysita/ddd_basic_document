# 解答しやすさレビュー

このskillは問題を**点検して報告するだけ**で、ファイルは変更しない。修正するかどうかはユーザーが決める。

## なぜこのレビューが必要か

このプロジェクトの問題集は、タイマーで1日1問ずつAIが出題・採点している。問題文が曖昧だと、ユーザーは何をどこまで書けばよいか分からず、AIは模範解答の言い回しと違うという理由で部分正解・不正解にする。実際に次のことが起きた。

- E4-06「性質の違いを説明せよ」：何を書けば正解か分からず、ユーザーが「答えづらい。曖昧すぎる」と指摘
- A-07：模範解答にあった教材にない一文（「従来TDDは開発者内部のプロセス」）を書かなかったため部分正解にされた
- A-01・A-04・A-06：本の一覧（3原則、3ステップ、5要因）を書き出させるだけで、ユーザーから「本の丸写しのような問題」と指摘

問題集の目的は、自分が実装するとき、DDDに基づいた設計を実行できる状態になること。教材の内容を暗唱したり、言い回しを当てたりする問題は、この目的に届かない。とくに、この本にだけ出てくる事例（SaaSovationなどのドメイン名・モジュール名）や、図表・ルールの番号を覚えていないと解けない問題は、設計の役に立たない暗記を求めている。DDDの一般的な用語・原則は覚える対象だが、本固有の事例は問題文に示して、設計の考え方で答えさせる。

## 手順

### 1. 読むもの

1. `.claude/skills/quiz-authoring/project.md`（習熟レベル、使ってよい形式、教材の場所）
2. 対象の問題ファイル（`問題集/{カテゴリID}_*.md`）
3. 対象章の `第XX章_*/第XX章まとめ.md` と `用語集/第XX章_用語集.md`（模範解答の根拠を確かめるため。必ず読む）
4. [references/examples.md](references/examples.md)（このプロジェクトで実際に見つかった欠陥と直し方。判定に迷ったら照合する）
5. `問題集/進捗/第1周_進捗.md` の対象カテゴリの行（結果とメモ）。不正解・部分正解の問題は、答えづらさが原因のことがある。判定の手がかりにしてよいが、結果だけを理由に要修正にはしない

問題に「ねらい」「採点の目安」「備考」の欄があれば読む。ねらいは点検の基準にする（問題がねらいを実際に確かめているか、ねらいが他の問題と重なっていないか）。備考の「課題」は既知の問題として扱い、解決済みなら指摘しない。「ねらい」の欄がない問題は、判定には影響させず、報告の「ほかに気づいたこと」に未記入の数を書く。

### 2. 1問ずつ、次の12観点で点検する

各観点は「回答者の立場で、この問題文だけを見て答えを書こうとしたら困るか」を自問して判定する。表現が違っても構造が同じ欠陥は同じ観点に当たる。

| ID | 観点 | 自問の仕方 |
|---|---|---|
| R1 | 答えの形が決まっているか | 答えの数・観点・範囲を、回答者が自分で決めなければならないか？（「説明せよ」「違いは何か」「何をしますか」だけで軸がない） |
| R2 | 正解が1つに絞れるか | 教材の別の箇所や他の問題の答えを書いても正解になりうるか？（例：「会話以外の使い道」→命名もテストコードも当てはまる） |
| R3 | 本独特の言い回しを再現させていないか | 正解するために、本の見出し・項目名を一字一句思い出す必要があるか？（例：「よいアーキテクチャに焦点を当てすぎる」を名前で答えさせる） |
| R4 | 一覧の書き出し（丸写し）になっていないか | 本の箇条書き・表をそのまま列挙させるだけで、理解や判断を確かめていないか？ |
| R5 | 問題文が答えをばらしていないか | 問題文の言葉から答えが直接わかるか？（例：「第1原則に従うと」→コアドメインに集中） |
| R6 | 勘・消去法・手がかり語で解けないか | 1対1対応の最後が消去法で決まる、状況文に答えの単語が入っている、上から順に当てはめれば正解、になっていないか？ |
| R7 | 模範解答が教材の範囲内か | 模範解答の各文が、章まとめ・用語集に根拠を持つか？教材にない推測・一般論・固有名詞（Stripe等）が混じっていないか？ |
| R8 | 1問1論点か | 定義・理由・比較・判断など、答え方の違う論点が1問に混在していないか？ |
| R9 | 採点がぶれないか | 内容は正しいのに言い回しが模範解答と違うだけで不正解にされそうか？（そうなら「採点の目安」を足す候補） |
| R10 | 他の問題・他の章と干渉しないか | 他の問題と論点がほぼ同じか？他の章（別カテゴリ）の内容を前提にしていないか？他の問題の答えをばらしていないか？ |
| R11 | 設計の実行に結びつくか | この問題で確かめる力は、実装するときのDDDに基づいた設計・判断に役立つか？教材の個別の記述を覚えているかを確かめるだけになっていないか？（状況を与えて判断・設計させる、理由を問う形が望ましい。知識確認は、設計判断の前提となる一般的な用語・原則に限る） |
| R12 | 本固有の内容の暗記を求めていないか | 正解するために、この本にだけ出てくるドメイン名・モジュール名・クラス名・図表やルールの番号・分類のラベルを覚えている必要があるか？必要なら、問題文に示す。DDDの一般的な用語・原則（エンティティ、集約など）は覚える対象なので、これには当たらない |

R7はとくに重要。教材にない内容を模範解答に入れると、ユーザーが正しく答えても減点される。疑わしい文は、章まとめと用語集を検索して根拠の行を確かめる。見つからなければ「根拠なし」と判定する。

R7は、模範解答だけでなく**状況文との突き合わせ**でも確かめる。シナリオ問題の模範解答が「〜は満たされている」「〜が欠けている」「〜に違反している」と判定している場合、その事実が状況文に実際に書かれているかを1つずつ確認する。書かれていなければ、回答者は別の判断をしても間違いと言い切れないので、R7（根拠なし）かつ R2（正解が複数）に当たる。

R7の判定線：
- 教材の文を同じ意味で言い換えたもの → 根拠あり
- 教材の文から直接読み取れない因果・理由・属性・具体例（「だからビルドが難しい」「インターフェイスである」「Stripeなど」）→ 根拠なし
- 教材の図・コード例と食い違うもの → 根拠なし（食い違いの内容を書く）

R6（常識だけで解けないか）：教材を読んでいない人が、常識だけで答えられるなら R6。「複雑で競争力のあるプロジェクトと、単純な社内システムのどちらにDDDを導入するか」のように、状況文の対比だけで答えが決まる問題が典型。答えの単語が状況文に反対語や同じ語で入っている場合（「兼任」→専任、「集まれる場所がない」→場所の確保）も同じ。

R6（手がかり語）の判定線：状況文に、分類の決め手そのものの言葉（「同じ意味で使っている」「定義が違う」など）が入っていれば軽度の R6。分類先が2つで各状況が自明に振り分けられるなら、使わない分類先を足すか、決め手の言葉を状況文から外すことを提案する。

R10の調べ方：問題ごとに、次の手順で他カテゴリを調べる。全問まとめて1回の検索で済ませない。
1. 問題の中心となる用語を2〜3語、状況文の題材（例：ECサイト、経費精算、与信審査）を1〜2語選ぶ
2. 対象カテゴリ以外の `問題集/*.md` から、見出し行（`^## `）と、題材の語を含む行を検索する。検索の対象にしない：`問題集作成_*.md`、`問題集の分類.md`、`進捗/`、`レビュー記録/`
3. ヒットした問題は、問題文と模範解答を読んで、論点が同じか（同じ観点で、同じ答えを求めているか）を判定する。題材が同じだけなら重なりではない
4. 重なっていた場合は、相手のIDを報告に書く（例：A-09 は Z-16 と重なる）
5. とくに Z_横断的問題、B（コアドメイン・BC）、D2（トランザクションスクリプト・貧血）は重なりやすいので、必ず見出しを確認する

1問が複数の観点に当たるときは、観点IDを併記してよい（R2とR7など、どちらか迷う場合も併記する）。

### 3. 判定

各問題を次の3つのどれかにする。

- **要修正**：R1〜R8、R10〜R12のどれかに当たる
- **採点の目安を追加**：問題文は良いが、R9に当たる（言い回しの許容範囲を模範解答に書けば足りる）
- **問題なし**

「技法を使っているから大丈夫」と早合点しない。シナリオや比較の形をしていても、答えの形が決まっていなければR1に当たる。

判定の約束：
- 点検した全IDを、どれか1つの区分にちょうど1回入れる。報告の最後に、3区分の件数を足して問題数と一致することを確かめる
- 前に同じ問題をレビューした結果が会話や記録にあるときは、判定が変わった問題を1行ずつ（前の判定→今回の判定、理由）示す。黙って変えない
- 問題の中に書かれていない前提（例：別の問題が未作成）に気づいたら、報告の最後に「ほかに気づいたこと」として書く

### 4. 報告の形式

次の形で報告する。指摘には必ず具体的な根拠（問題文のどの言葉が、どう困るか）を書く。

```markdown
## 要修正（N問）

| ID | 観点 | 何が答えづらいか | 直し方の案 |
|---|---|---|---|
| A-06 | R3, R6 | 5要因を本の名前で答える必要がある。ウ・オは状況文に「アジャイル」「テスト」があり自明 | 要因名を分類先として示し、使わない分類先を1つ混ぜる |

## 採点の目安を追加（N問）

| ID | 何が起きるか | 目安の案 |
|---|---|---|

## 問題なし（N問）

| ID | 理由 | 軽微な注記（なければ空欄） |
|---|---|---|
| A-02 | 答えの数が問題文で決まり、状況から答えが1つに絞れる | |
```

直し方の案は、project.md で使ってよい形式（記述式中心、例外として分類形式）の範囲で考える。分割が必要なら、何と何に分けるかまで書く。

報告の書き方：
- 報告全体を日本語で書く
- 削除・統合が必要そうな問題は、自分で決めず、選択肢を2つ示してユーザーに選んでもらう。削除の選択肢には、IDに欠番ができること（後続のIDはずらさない決まりのため）を書く
- 最後に、どの問題から直すかをユーザーに尋ねる。修正は1回の応答で1問ずつ進めることも伝える
- スキルの指示で分かりにくかった点があれば、1行で書く

報告したら止まる。修正はユーザーの指示を待ってから、quiz-improvement-workflow の手順で1問ずつ行う。

## 直し方の定石

| 欠陥 | よく効く直し方 |
|---|---|
| R1 答えの形が不定 | 答えの数・軸を問題文で指定する（「2つ挙げ」「誰と・いつから」「〜の観点から」） |
| R2 正解が複数 | 比べる相手を問題文に入れて絞る（「データ構造ではなく何を基準に」） |
| R3 言い回しの再現 | 名前を問題文に示して分類させる／名前ではなく内容で答えさせる |
| R4 一覧の書き出し | 欠けている状況・誤った発言を示し、どこが足りないか・誤っているかを指摘させる |
| R5 答えのばらし | 問題文から答えの言葉を外す。「どの原則に基づくかも答えよ」のように回答者に特定させる |
| R6 消去法・手がかり語 | 使わない分類先を1つ混ぜる、状況文から答えの単語を外す、並び順をずらす、決め手を1文書かせる |
| R7 根拠なし | 根拠のない文を模範解答から削る。問題文もその部分を問わない形に直す |
| R8 複数論点 | 枝番で分割する（`A-06` → `A-06-1`、`A-06-2`。後続のIDはずらさない） |
| R9 採点ぶれ | 模範解答の後に「採点の目安：〜という内容が書けていれば正解。〜という言い換えも可」を1行足す |
| R10 干渉・重複 | 重複なら統合・削除、他章の内容なら該当章の範囲に絞る |
| R11 設計に結びつかない | 状況を与えて「どう判断・設計するか」を問う。教材の記述の再現だけを求める問いは、設計判断の前提になる一般的な用語・原則の確認に絞る |
| R12 本固有の暗記 | 本固有の名前・番号・ラベルを問題文に示し、答えは設計の考え方（理由・判断）で出せる形にする。例：モジュール名を示して各部分の意味を聞く、ルールの一覧を示してどれに反するかを聞く |
